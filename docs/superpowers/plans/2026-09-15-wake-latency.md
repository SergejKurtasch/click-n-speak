# План уменьшения задержек после сна и остановки записи

> Для исполнителя: выполнять задачи последовательно через навык `executing-plans`. Сначала проверять воспроизводящий тест, затем менять код и выполнять соответствующие проверки. Этот документ описывает будущую реализацию; приложение и пользовательские настройки при подготовке плана не изменялись.

**Цель:** раньше показывать распознанную речь, устранить холодный первый вызов Qwen после пробуждения и сократить ожидание очереди Whisper без потери речи и ухудшения согласованного качества.

**Архитектура:** SessionController публикует предварительный текст до AI-редактуры. Прогрев активного локального редактора проходит через AiEditorRouter и общий InferenceExecutionGate; SessionController владеет задачей до фактического завершения вычислений. Выбор Whisper и параметров фрагментации опирается на измерения реального конвейера RU+EN.

**Стек:** Swift 6, SwiftPM, AppKit, whisper.cpp, MLX Swift; Python из проектного venv для анализа измерений. Новые зависимости не требуются.

**Основание:** запрос пользователя от 15.09.2026 и диагностика в текущем обсуждении; AGENTS.md; рабочий лог `~/Library/Logs/Click-n-speak.log`.

Три направления реализации:

1. Ранний предварительный показ текста.
2. Управляемый прогрев Qwen после пробуждения.
3. Ускорение распознавания и опустошения очереди: сравнение Large v3 / Turbo, затем при необходимости проверка более раннего разделения аудио.

### Общие ограничения

- Сохранять пользовательские изменения, выделение, исходный target PID и provenance PopupDraft при добавлении записи.
- Обрабатывать все принятые фрагменты по порядку. Не отбрасывать короткую реальную речь ради скорости.
- Предварительный текст не записывать в историю, dataset или анализ исправлений; это делает существующее подтверждение пользователя.
- Whisper и Qwen используют общий InferenceExecutionGate. Отмена задачи не означает немедленное завершение GPU-операции.
- Не освобождать lease, экземпляр модели или runtime reservation до фактического завершения соответствующей операции.
- UI изменяется на MainActor. Результат старой сессии или поколения прогрева не меняет новую сессию.
- Прогрев не загружает отсутствующую модель, не обращается к облачному редактору и не меняет выбранный backend.
- Runtime-события содержат только длительности, идентификаторы, счётчики и исходы. Не ослаблять существующий фильтр конфиденциальности.
- Все проверки запускать после `source venv/bin/activate`, включая команды Swift согласно политике проекта.
- Изменения реализации, тесты, комментарии и коммиты — на английском; локализованные пользовательские строки — на соответствующих языках.
- Рабочее дерево уже содержит изменения определения языка в CNSTranscription и CNSSession. Они не входят автоматически в этот набор исправлений; базу сравнения нужно зафиксировать явно.

Точная функция расчёта для анализатора:

```python
def delay_after_stop_ms(
    stop_uptime: float | None,
    presentation_uptime: float | None,
) -> float | None:
    if stop_uptime is None or presentation_uptime is None:
        return None
    if not math.isfinite(stop_uptime) or not math.isfinite(presentation_uptime):
        return None
    return max(0.0, presentation_uptime - stop_uptime) * 1000.0
```

Тест расчёта:

```python
    assert delay_after_stop_ms(10.0, 9.0) == 0.0
    assert delay_after_stop_ms(10.0, 12.5) == 2500.0
    assert delay_after_stop_ms(10.0, None) is None
    assert delay_after_stop_ms(None, 12.5) is None
```

### Автоматические проверки

Для проверки порядка использовать управляемую приостановку FakeAiEditor: тест ждёт входа в `refine`, проверяет UI и только потом разрешает редактору вернуть результат. Добавить в FakeAiEditor опциональный `RefinementBarrier`; у barrier методы `pause() async`, `waitUntilEntered() async`, `resume()`, реализованные через actor и checked continuations. `resume` разрешает и уже ожидающий, и следующий `pause`, поэтому порядок доставки не создаёт гонку.

Тест внутри существующего SessionControllerTests после добавления barrier:

```swift
@Test("The final transcript is visible while refinement is suspended")
func finalPreviewPrecedesRefinement() async {
    let barrier = RefinementBarrier()
    let editor = FakeAiEditor(refinementBarrier: barrier)
    editor.refinedText = "Edited result."
    var config = Self.makeConfig()
    config.raw["ai_editor_enabled"] = .bool(true)
    let rig = makeRig(texts: ["Raw result"], config: config, aiEditor: editor)

    await runSession(rig)
    await barrier.waitUntilEntered()
    #expect(rig.panel.events.contains(.text("Raw result")))
    #expect(rig.panel.interactiveTexts.isEmpty)

    await barrier.resume()
    await settle()
    #expect(rig.panel.interactiveTexts == ["Edited result."])
}
```

Обязательные дополнительные сценарии:

| Сценарий | Проверяемое поведение |
|---|---|
| Один финальный фрагмент | Текст виден до возврата editor.refine |
| Несколько фрагментов | Видимая полная версия содержит последний фрагмент до AI |
| AI timeout/error/skip/disabled | Речь сохраняется, окно становится интерактивным один раз |
| Append после ручных исправлений | Старый текст и выделение не изменяются от preview |
| Append + тишина/неуспешный старт | Восстанавливается тот же draft, временный блок пуст |
| Поздний callback после shutdown | Окно не открывается заново |
| Неполная транскрипция | Предупреждение сохраняется; обучение не включается |
| Подтверждение | Одна запись в dataset с фактическим финальным пользовательским текстом |


Реализация по умолчанию возвращает `.skipped`. Облачный и выключенный редактор не выполняют запросов. AiEditorRouter получает активный Entry, вызывает beginUse, ждёт preWarm и только затем вызывает endUse, как для refine.

Этот метод возвращается только после завершения реальной вычислительной задачи, включая завершение после отмены. Обычный `generate` сохраняет свой публичный контракт.

### Критическая деталь MLX

В установленной версии `ChatSession.respond` читает AsyncStream, за которым работает отдельная задача. Окончание чтения при отмене не является достаточным доказательством завершения GPU.

В синтетическом пути использовать `ModelContainer.perform`, `TokenIterator` и `MLXLMCommon.generateTask`. Сохранять возвращаемый `Task<Void, Never>`. Принцип завершения:

```swift
await withTaskCancellationHandler {
    for await _ in stream {
        if Task.isCancelled {
            generationTask.cancel()
            break
        }
    }
    await generationTask.value
} onCancel: {
    generationTask.cancel()
}
try Task.checkCancellation()
```

Здесь `stream` и `generationTask` — пара, возвращённая `generateTask`. Lease принадлежит внешней операции и освобождается после этого блока. Проверять отмену также до подготовки input и перед созданием TokenIterator. Зависимость MLX не модифицировать.

### Последовательность

1. Получено didWake. Предыдущий отложенный запрос этого поколения отменяется; создаётся один новый.
2. Через 1 с выполнить проверку истинного idle. Пауза даёт системе закончить первичное восстановление; она не находится в обработчике горячей клавиши.
3. Выполнить существующий прогрев Whisper.
4. После каждого await проверить UUID операции, отмену, shutdown, поколение runtime и отсутствие нового пользовательского действия.
5. При trigger `.wake` или `.startup` прогреть активный готовый локальный редактор через router. После wake передавать `force: true`.
6. Завершить операцию и снять reservation только после фактического завершения обоих компонентов.

После начала собственной операции не использовать `isRuntimeIdle` напрямую для перехода Whisper → Qwen: эта проверка уже false из-за самого warmupTask. Проверять остальные признаки занятости и владение текущим UUID отдельно.

Дополнительные правила:

- [ ] Подписать lifecycle на willSleep: отменить отложенный запуск и активный синтетический прогрев. DarkWake без пользовательского пробуждения не должен создавать цепочку повторных прогревов Qwen.
- [ ] Состояние lifecycle и уведомления тестировать через инъекцию NotificationCenter и планировщика задержки; тесты не должны усыплять компьютер.
- [ ] События пробуждения объединять в один pending intent. Если runtime ещё подготавливается, выполнить intent один раз после перехода в ready при настоящем idle; не запускать бесконечные таймеры повторов.
- [ ] Новая запись, запуск file job, смена runtime, повторный сон и shutdown отменяют pending intent. Начатая операция остаётся учтённой до завершения.
- [ ] `beginStart()` вызывает cancelWarmup синхронно и продолжает запуск захвата. `transcribeFile()` сначала сохраняет ссылку на текущую задачу прогрева, запрашивает её отмену и ожидает завершение; после await повторно проверяет Task.isCancelled, runtime availability и настоящий idle перед резервированием file job. Конкурирующая запись может занять сессию во время ожидания — тогда file job возвращает штатный busy result.
- [ ] AppRuntimeCoordinator вызывает cancelWarmup перед существующим `waitUntilSessionIsIdle`, затем сохраняет действующие проверки generation. Полузафиксированную замену STT/editor этим механизмом не отменять.
- [ ] Запись может начать захват аудио сразу после запроса отмены прогрева. Первый STT-запрос получает общий gate только после завершения синтетического вычисления; возможную задержку этого освобождения измерять отдельно.
- [ ] Отмена прогрева редактора не вызывает `transcriber.abortInFlight()` для уже начатой пользовательской транскрипции. Abort Whisper применять только к принадлежащему этой операции синтетическому STT.
- [ ] После отмены прогрева Whisper не переходить к запуску Qwen.
- [ ] `isRuntimeIdle` и `pendingShutdownActivities()` учитывают всю составную операцию; при не завершившейся отмене shutdown возвращает `.warmup` как pending.
- [ ] 15-минутный keepalive сохраняет прежний прогрев Whisper. Qwen не запускать каждые 15 минут всю ночь: первое включение механизма ограничить startup и wake.
- [ ] Не передавать исходы Qwen в TranscriberHealthMonitor и не перезапускать Whisper из-за неудачного прогрева редактора.

### Целевые показатели

| Показатель | Критерий |
|---|---|
| Задержка UI после последнего STT | ≤100 мс при обычной нагрузке |
| Qwen на первой короткой записи после завершившегося прогрева | Медиана ≤2,5 с и ≤1,5× сопоставимого тёплого контроля |
| Очередь/распознавание при смене модели | Относительные критерии задачи 5 выполнены |
| Готовность к Enter после сна | Близка к тёплому контролю того же текста; целевой ориентир 4–6 с для коротких записей, окончательное число определяется моделью и очередью |
| Реальная запись прерывает прогрев | Нет потери аудио; освобождение GPU измерено, целевой ориентир ≤1 с |
| Сохранность данных | Ноль потерянных/повторённых фрагментов и перезаписанных пользовательских правок |
| Поведение под ошибкой/отменой | Нет позднего открытия окна, преждевременного освобождения модели и ложного успешного shutdown |

### Откат

- Для проблемы в UI вернуть только предварительный показ, сохранив финальную обработку и остальные исправления.
- Для проблемы отмены прогрева отключить его запуск из lifecycle; не освобождать принудительно ещё занятую модель.
- Для ухудшения качества Turbo вернуть Large v3 через существующий runtime transaction; файлы моделей сохранять.
- Не откатывать вместе с этим независимые пользовательские изменения определения языка.
